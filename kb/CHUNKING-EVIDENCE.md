生产默认配置是 **行组袋 + 纯 text + `KB_CTX_CHARS=0` + `KB_EMBED_HEADING=0`**，四个文档域（main / zh / comp，epi 是蒸馏条目）一致。

| CTX 散文窗 | 【实测】五档与对照臂逐题相同（57/1746 块文本变了，0 题名次变） | 结构性无效（0 张表） | 与关闭档逐题相同 | 默认关 |

## 2. 判据与实验纪律（先声明，后开跑）

一次切块/嵌入改动要被采纳，必须同时满足：

1. **锚点完整性**：gold_anchor 在对比臂里仍完整落在单个块内（comp 43/43、zh 40/40）。不做这步，分数变化可能只是"切块把证据劈开"。
2. **单变量**：切块、嵌入约定、融合档一次只动一个；对照臂共用同一份 BM25 或同一份 chunks。
3. **过机器闸门**：hit@5 与文件级@5 同时达标；只涨一档不算。
4. **隔离目录**：实验写 `ab_*/` 或 `kb/scratch/`，生产 `chunks.jsonl`/`vec.npy` 一个字节不动。
5. **可回退**：换档前把三件（chunks/vec/bm25+vocab）和 baseline 打包进 `snapshots/`。
6. **受控多轮**：调参与机制改动不做单次测速（见用户规程 feedback-controlled-ab-for-tuning）。切块/评测是确定性计算（同一 chunks 同一 BM25 同一 vec → 名次逐题相同），"多轮"在这里的正确用法是**多臂同代对照 + 多场景子集**，不是把同一次跑重复三遍。
7. **对照臂必须同代切块**：拿今日 chunker 的臂去比冻结的 V3（1436 块/88 文件）无效——今日默认参数同语料切出 1745 块/102 文件（V3 的 88 文件一个不少，多 14 个），只有 1154 个 id 与 V3 重合，且实测 **base 臂 80.0%/文件级 100.0% 本身就低于 V3 的 hit@5 闸门**。所以每个杠杆都跟**同代 base 臂**比，V3 闸门只作为换档上线的绝对门槛另算。

## 3. 逐项证据

### 3.1 CTX：表格块挂上方散文窗（`KB_CTX_CHARS`，默认 0）

实现：`chunker.py:_ctx_of` 取表格/代码块**上方紧邻散文的最后几句**（句子对齐、不截半句），字符上限即 `KB_CTX_CHARS`；上方是标题或表格本身时不给前缀。

- **竞品库【实测】**（`CORPUS-COMP-REPORT.md` §6.1/§6.2）：
  - A（CTX=0）2442 块 vs C（CTX=600）2446 块：BM25 两臂 88.4% / MRR .661 vs .660 / 文件级 95.3%，**词表同为 14493、未命中集合逐题相同** → 该开关不改词面，胜负只能看 dense。
  - dense：A 74.4% vs C 74.4%；hybrid-v2：两臂 81.4%，**逐题命中完全相同**；C 的 vec hit@1 48.8% vs A 51.2%（微负）。
  - B（CTX=600 + 拼标题）：dense 72.1%，semantic 子集 56% vs A 67%，hybrid-v2 仍是 81.4%——top-5 没增，只是排序前移（MRR .686）。
  - 裁决：**零到微负；`KB_CTX_CHARS=0`**。
- **展会专利库【实测】**：33 个 md 里 markdown 表格 0 张（唯一含 `|` 的文件是绝对值符号），`kind=table` 计数为 0 → 开关没有作用对象（§7.3）。
- **主库【实测】（2026-11-03 晚，`kb/scratch/{base,ctx}` 同代双臂）**：`KB_CTX_CHARS=600` 下 ctx 1746 块 vs base 1745 块，**1735 个 id 相同**，其中 **57 块文本发生变化**（56 块是纯挂前缀，平均前缀 **160 字**——远没吃满 600 的窗，说明上方本来就没什么散文）、另有 ctx 侧 11 个新 id / base 侧 10 个消失（前缀把袋撑过预算造成的边界位移）；真正被挂上散文前缀的**表格块只有 9 个**（如 `plc-14-data-logging.md` 的 6 列表格前那句"说明：D1000~D1199 为 SPC_DATA 区"、`BENCHMARKS.md` 的 KV 表前一句英文结论）。五档评测**与 base 逐题完全相同**——grep/bm25/vec/hybrid/hybrid-v2 全部 21.8/67.3/63.6/76.4/**80.0%**，文件级 100.0%，MRR .577，未命中集合 11 题一字不差，**55 题 × 4 档零名次变化**。
  - 方法坑（本轮踩过）：比两臂块差异**必须按 `id` 比，不能按位置 `zip`**。按位置比会因为一次 +1 块的位移把 57 虚报成 281——这种假增量会让人以为开关起了作用。
- **为什么零变化——语料普查【实测】**（`kb/scratch/above_ctx_census.py`，只统计唯一能被 CTX 触及的"表格段 ≥800 字"）：
  - main：78 张长表，**89.7% 上方紧邻的是标题**（`_ctx_of` 对标题直接返回空），真散文只有 8 张，其中 ≥80 字的说明 **3 张**；
  - comp：137 张长表，**70.8% 上方是 <30 字的抽取残留**（`@@PAGE 7@@` / `目录` 这类页码与 TOC 引导行），≥80 字真说明 **1 张**；
  - zh：全库长表 1 张，上方无散文；`<本地专利 PDF 目录>` 只有 33 个 PDF（无文本语料），`竞争对手\CHM_full_text.txt` markdown 表格 0 张。
  - 四条件联合判据（≥6 列 ∧ terse 单元格占比 ≥0.5 ∧ 上方 ≥80 字 CJK 散文 ∧ 表身 ≥800 字）在全部 1007 张表（其中长表 222 张）上命中 **0 张**（`kb/scratch/wide_table_probe.py`）。
- 裁决：**CTX 在主库同样无收益场景，`KB_CTX_CHARS=0`**。它不是"参数不够好"，是**没有作用对象**——本库表格上方普遍是标题，而标题已经由 `heading` 元数据带进 BM25 与（可选的）嵌入侧。

### 3.2 嵌入文本回填祖先标题链（`KB_EMBED_HEADING=1`，默认 0）

实现：`build_vec.py` 在嵌入文本前拼上块的祖先标题路径；落库 chunks 文本不变（金标准锚点不受影响），只改向量侧输入。

- **主库 V5h【实测】**：V4 块 1780 + 拼标题，hybrid-v2 **78.2%**、MRR .533、文件级 94.5%，FAIL。dense 63.6→65.5 回升，但混合档一分未涨。
- **竞品库 B 臂【实测】**：dense 72.1% vs A 74.4%（−2.3pp），semantic 56% vs 67%（−11pp），hybrid-v2 81.4% 持平 → 用语义召回换词面排序。
- **专利库 H 臂【实测】**：dense 85% vs P 75%（+10pp，是唯一 dense 明显上涨的域），但 hit@1 52.5% vs 60%、MRR .685 vs .713，hit@5/文件级并列 → 按"并列取简"选 P（纯 text）。
- **跨域模式【实测+推断】**：拼标题稳定改善 dense 近邻结构，但**从未转化为 hit@5 增量**，还会在融合后压低 hit@1/MRR。三个域同向，杠杆正式关闭，不再重试。

### 3.3 行原子化（`KB_ROW_ATOMIC=1`，默认 0）

超长表格一行一块、表头每块重复。主库【实测】dense 63.6%，FAIL。原因：行与行共享表头模板，在嵌入空间里近似重复，把 dense 召回打散；同时一行块缺上下文，语义题直接失分。

### 3.4 行组袋（默认行为，不是开关）

超过 `MAX_CHARS=800` 的段落/表格按行装袋，表头每块重复，行组共享预算。它不是质量杠杆，而是**兜底机制**：保证超长表格不会撑爆单块，也不会被句子切分切成半行。

- 主库 V4 把它当作手术主刀（1436→1780 块）【实测 78.2% FAIL】：词面涨（61.8→65.5）、dense 掉（69.1→63.6），净负。
- 竞品库/专利库重切后仍用它【实测】：COMP-v2 83.7%、ZH-v2 87.5%，无退化——说明它在"本来就有超长段"的语料上只是兜底，不产生增量也不制造损失。
- 结论：保持默认，但**不要为了用它而重切主库**。

### 3.5 节内去重【实测】

只能救回 q027 一题，同时让 q003 的证据永久不可达（同一句在两个小节重复出现时，删掉的那份可能正是 gold 所在）。不采纳。

### 3.6 BM25 长度归一 b 扫描【实测】

b ∈ {0.4, 0.75, 1.0}，最好 67.3%（+1.8pp），离闸门差距过大。保持 b=0.75。

### 3.7 融合权重 w 扫描【实测】

min-max 权重 w=0.6 时 hit@5 80.0%，但文件级掉到 96.4%（闸门 96.36% 边缘），不过闸。保持 0.5:0.5。

### 3.8 armB：每行追加「列名=值」（`KB_ROW_NL=1`，默认 0）

- **收益（早期【实测】）**：BM25 69.1%（1922 块，较 V3 的 61.8% +7.3pp），0 锚点破坏——迄今最好的词面杠杆。
- **原阻塞**：`_cols_of` 过滤空列名导致整行左移，产出 `MTT S80=MUSA 核心` 这类错配标签，等于把假事实写进索引。
- **修复（2026-11-03，#24）**：空列名保留占位；表头必须"首行 `|` + 第二行分隔行"才成立，避免两行小表把首条数据行当表头吞掉。
- **完整五档评测【实测】（2026-11-03 晚，同代双臂 `kb/scratch/{base,armB}`，base 全量重嵌 1745 块 / armB 按内容哈希复用 1592 块、只嵌 292 块）**：

  | 档 | base（1745 块） | armB（1884 块） | Δ |
  |---|---|---|---|
  | bm25 | 67.3% / 文件级 87.3% | **69.1%** / 89.1% | **+1.8pp**（词面确实涨，历史结论复现） |
  | vec | 63.6% / 92.7% | 63.6% / 92.7% | 0（MRR .447→.457） |
  | hybrid(RRF) | 76.4% / 96.4% | 74.5% / 96.4% | −1.9pp |
  | hybrid-v2 | **80.0%** / **100.0%** | 76.4% / 98.2% | **−3.6pp / −1.8pp**，MRR .577→.588 |

  逐题看：bm25 档 11 题名次变化、8 好 3 差（q007 None→5、q022 None→6、q026 4→2 是被标签救回的表格行题；q034 1→5、q048 5→None 是被标签挤掉的）；hybrid-v2 档 14 题变化、7 好 7 差，净负。
- **裁决：不采纳**。"+7.3pp 的最好词面杠杆"在融合后不成立——合成标签把列名重复进每个数据块，BM25 侧收益只有 +1.8pp，dense 侧持平，而块数 +139（+8%）稀释了候选池，双档净负。另外合成标签本质是**改写语料**（把表头解释钉进行文本），一旦表头与数据行错位就是假事实，风险不对称。
- 【推断】若要再撬词面，方向不是往块里钉标签，而是让 BM25 在表格块上**降低长度归一惩罚**（`KB_B` 扫描已试，3.6 证伪）。精排路已在 3.11 实测出局（bge-reranker-base 在 V3 上把 81.8% 打成 60.0%，"表格行类更准"的旧结论作废）。

### 3.9 重切时的三个正确性修复（非策略，必须保留）

2026-11-03 晚对 comp/zh 重切，收益来自三个 bug 修复，不是参数调优：

1. **超长段双写**：超长段句切分支里 `buf` 未清空，同一块被写两遍（旧 comp 库 49 对完全重复块，白占 top-k 名额）。
2. **两行小表吞数据行**：旧实现只认前两行以 `|` 开头就判表头，首条数据行此后不出现在任何块里。
3. **行号回搜错位**：旧实现按块首行文字回搜原文，同节重复首行（表头、空标题）会命中前一处的行号。改为切块时直接携带字符偏移。

【实测】comp 2442→2388：hybrid-v2 81.4%→**83.7%**，文件级 95.3% 不变，MRR .670→.672，dense 74.4%→72.1%（代价）；行号准确率 78.8%→100%。
【实测】zh 548→547：分数不变（87.5%/100%，MRR .713），行号准确率 58.4%→100%，向量按内容哈希复用 547/547 行、0 块重嵌。

### 3.10 语义切块 / 块间重叠【推断，未在本库 A/B】

本工作区早期调研与外部实践（RAGFlow/LightRAG 的 V/P/R 分块文档）给出的成本结构：语义切块要逐句求嵌入、对中文长文成本高且块边界不稳定；重叠窗会制造近似重复块，与 3.9-1 实测的"重复块白占 top-k"同向。本库没有直接数字，标注为推断。**不采纳的理由是成本/风险，不是已证伪**；若将来有语料在 V3 配置下 semantic 子集长期低于 60%，可作为下一轮候选，但必须先过闸门。

### 3.11 精排档 hybrid-r（bge-reranker-base）【实测，出局】

2026-11-03 在 V3 生产档（同 1436 块、同金标准）补测 hybrid-r：hybrid(RRF) 粗排 top-20 → 交叉编码器精排。

| 档 | hit@1 | hit@3 | hit@5 | MRR | 文件级@5 | 单查延迟 |
|---|---|---|---|---|---|---|
| hybrid-v2（生产） | 45.5% | 67.3% | **81.8%** | .583 | 96.4% | 毫秒级 |
| hybrid（RRF，精排的粗排底子） | — | — | 78.2% | — | — | 毫秒级 |
| **hybrid-r** | 38.2% | 52.7% | **60.0%** | .487 | 92.7% | **21.9–23.6s** |

分题型 hit@5：keyword 77→**68**、semantic 80→**40**、multi 92→**77**——全线下跌，semantic 最惨（交叉编码器接不住改写类查询，回退成词面偏好排序）。

**22 道落空题拆解**（`kb/scratch/rerank_diag.py`）：粗排池里根本没有 gold 8 题（精排无力回天，非其罪）；gold 在粗排 6~20 名、精排没捞进@5 只 1 题（"从深池捞回"的能力基本不存在）；gold 本在粗排@5 **被精排挤出去 13 题**，救回只有 3 题——净伤害 −10 题 = −18.2pp。

**因果定位**：挤掉组的 480 字截断暴露率 2/13（≈ 全库基线 7/54，无相关性）——掉分主因不是 `p[:480]` 截断，而是**精排模型自身的排序分歧**：bge-reranker-base 对中文技术表格/参数语料的判断与调好的 min-max 融合方向相反。旧口径"精排对表格行类问题更好"是 e5 时代相对弱基线的结论，在 V3 上被推翻。**裁决：不进默认档，也不作为深挖档推荐**；若将来要精排，先换更强的中文重排模型重测同闸门，而不是调 bge-reranker 的参数。

## 4. 新增语料域的标准动作

1. **先量语料性质**：文件数、字数、markdown 表格数（`kind=table`）、超长段比例。没有表格的域，CTX 直接排除。
2. **用 A 配置建库**：行组袋（默认）+ 纯 text（`KB_EMBED_HEADING=0`）+ `KB_CTX_CHARS=0`。
3. **金标准用 regex 探针构造**：锚点从原文原样取出，再做跨文件唯一性与落块检查（参考 `kb/gold_comp.py`）。
4. **先落闸门再挂服务**：写 `<kb_dir>/baseline.json`（精确分数 + 回滚件路径），跑 `eval.py` 确认 PASS，再注册到 8310。
5. **要动开关就单独开臂**：写隔离目录、同 BM25/同 chunks 对照、先过锚点完整性，再比 hit@5+文件级；不过闸就把数字记进本档，不重试。

## 5. 重测协议（armB 或者将来任何一刀）

```bash

# 1) 隔离目录切块（不碰生产）
KB_ROW_NL=1 venv/Scripts/python.exe -X utf8 kb/chunker.py --root <corpus> \
```
