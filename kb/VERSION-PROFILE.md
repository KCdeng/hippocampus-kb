## 4. 强项

1. **词面与语义互补，不是单档堆料**：单档最高只 69.1%（vec），融合到 81.8%；语义题从 bm25 的 45% 拉到 80% 完全靠混合。
2. **定位即可引证**：重切后行号准确率 100%，返回 `file + line + heading + 120 字摘要`，`read_chunk` 再取原文窗口，写引证不需要二次搜索。
3. **往返经济性**：任务级实测 1 次查询顶 grep 的 5.5 次往返，注入字数省 44%——长会话里这条比 hit@5 更值钱。
4. **退化会被机器抓住**：`baseline.json` 闸门（不过闸 exit 1）、chunker 块数守卫、chunks/bm25/vec 行数断言、vec provenance、`replay.py` 前后 top-5 diff。本轮 base 臂 80.0% 就是被这套拦下来的，不是靠人记住。
5. **中文技术文档友好**：jieba 用户词典＋ alias 运行时扩写是主要增量来源；改词典须全量重建 BM25，改 alias 由监视器清缓存（通常 ≤10s），也可重载 main 立即生效。
6. **记忆与文档不抢权**：tiered 布局、superseded×0.3×confidence、`mem_audit` 居中余弦查冲突。

## 5. 弱项

1. **top-1 不可靠（45.5%）**：命中通常要读到第 2–5 条，仍依赖调用方阅读复训；精排档 `hybrid-r` 不是解药——V3 上实测 hit@5 60.0%（keyword 68 / semantic 40 / multi 77），比生产档 81.8% 低 21.8pp，且 22s/查，已出局（CHUNKING-EVIDENCE §3.11）。
2. **约 1/5 的问题查不到**（10/55 未命中），且其中 q053 属于**切块把证据劈开**——切块本身仍是已知缺陷面。
3. **表格行级数值问题没有对症杠杆**：CTX 与 armB 双双证伪（见 CHUNKING-EVIDENCE §3.1/§3.8），语料普查显示"宽表 ∧ 表外说明"目标表 0/1007 张——是真没有场景，不是没调好。
4. **热重载仍有进程级边界**：chunks / 新增记忆可 `POST /reload` 原子热重载，失败保留旧档；alias_map 由监视器清缓存，自动监视通常 ≤10s 追上。服务代码、模型和端口配置变更仍需重启；端口已有监听者时新实例会明确 `FATAL` 并以退出码 1 退出，不再静默双开。
5. **覆盖盲区**：根层规程文件（`agents.md` 等 14 个）不在 V3 索引里；今日 chunker 能切到，但同时会把 `_tmp_frames/` 234 块中间件灌进候选池（13.9%），换档前必须先归因（CHUNKING-EVIDENCE §7.4）。
6. **评测集小**：55/40/43/12 题，二项噪声 ±8pp；comp 文件级余量 0.3pp，一次语料增补就可能翻车。
7. **内存与跨进程耦合已缓解但未解耦**：zh 的 e5 改为首查懒加载，m3 仍常驻共享；9.2GB 是旧全预热口径，新 RSS 待严格复测。8310 与 Hermes 启动时核对 main/zh/comp 的 vec provenance：main 模型不一致即拒绝挂载，zh/comp 不一致则不挂载该区并告警，防止共用磁盘索引时静默换档；Hermes 运行进程需重启后才吃到同款校验。

## 6. 派活指南

**该派给它的**

| 场景 | 为什么 | 依据 |
|---|---|---|
| 术语/型号/地址/报警码定位（PLC 地址表、HMI 元件、某同业机型/某伺服机型 参数与报警、vLLM 部署结论） | keyword 77%、multi 92%，0.1s 出 file:line | §2.1 |
| 写方案/专利取证时的引证 | 行号 100% ＋ heading ＋ 摘要，配合 read_chunk 精读 | §3、§4.2 |
| 长会话里反复回到同一批文档、长文档摘要前定位 | 往返 5.5→1.0，注入省 44% | §2.3 |
| 中文专有名词与别称 | 用户词典＋alias 扩写 | §4.5 |
| 记忆/复盘当线索不当结论 | tiered 附后＋×0.3 衰减 | §4.6 |

**别派给它的**

| 场景 | 为什么 | 替代做法 |
|---|---|---|
| 要求第一条就命中的高精度问答 | hit@1 45.5% | top-3 全读（精排档已实测更差，别用） |
| 概念性"这方案行不行"的开放推理 | 纯 vec 69.1%、semantic 80% 是混合档给的 | 多轮查询改写，别指望一次 |
| 表格行级数值枚举 | CTX/armB 出局、q053 劈块 | 直接 `read_chunk` 原文件（精排档已实测更差，别用） |
| 高频批量（>个位数 QPS）、内存紧张机器 | 9.2GB 常驻、CPU 嵌入 19min/千七百块 | 服务器侧先探测再定 backend |
| 索引刚改完立刻查 | 自动监视有秒级延迟 | `POST /reload {"zone":"..."}` 后立即查，并看 `/stats` 的 `reload`；失败会保留旧档 |

**默认口径**：`hybrid-v2` 定位 → 精读出处段落 → 引用 `file:line`；服务不可用或索引明显过期就回退 grep 并在答复里注明。
