# 架构：五个区与一条查询链路

海马体（hippocampus）是一个**跑在个人服务器上的本地知识库检索引擎**：文档以 Markdown 落盘，
切块后同时建 BM25 稀疏档与 dense 向量档，查询时融合两路排序，常驻 HTTP 服务把五个区一起放在内存里。
它不是数据库，也不是向量库的封装——全部代码约三千行，没有服务依赖，磁盘上的文件就是真相。

## 五个区

| 区 | 装什么 | 默认档位 | 是否进默认查询 |
|---|---|---|---|
| main | 工作区文档（设计笔记、手册、结论） | bge-m3 + hybrid-v2 | 是 |
| mem | 智能体写回的会话结论（带 confidence 与 superseded 指针） | bge-m3 + hybrid-v2 | 是，排在文档之后 |
| epi | 周期性复盘蒸馏出的经验教训候选 | bge-m3 + hybrid-v2 | 需人工 promote 才可见 |
| zh | 专利文本 | multilingual-e5-large + hybrid(RRF) | 显式 `kb=zh` 才查 |
| comp | 竞品文本 | bge-m3 + hybrid-v2 | 显式 `kb=comp` 才查 |

每个区是一个**自洽目录**：`chunks.jsonl`（切块正文）、`bm25.npy` + `bm_vocab.json`（稀疏档）、
`vec.npy`（dense 档）、`meta.json`、`baseline.json`（该区的机器闸门）。区与区之间不共享倒排表，
所以换档、重建、回滚都可以只动一个区。

## 一次查询走的路

`POST /search` 收到 `query` 后：查询切词（jieba，带用户词典）→ 别名扩写 → BM25 打分；
同一条查询文本做一次 dense 嵌入（请求内复用，不再每档重嵌）→ 与稀疏档融合 → 按 `layout` 排版返回。
默认 `layout=tiered`：文档区结果在前、智能体记忆在后，两段各自带来源文件名与行号，
调用方可以拿着行号回去精读原文。**记忆区结果只当线索用**，因为它记录的是"当时得出的结论"而不是证据。

## 为什么不做成交互式 agent 的一部分

检索这一层必须比调用它的智能体**更笨、更可预测**：同一句查询返回同一批块，改动只能靠机器闸门放行。
把判断留给智能体，把一致性和可回滚留给引擎——这是整个项目唯一的设计约束。
